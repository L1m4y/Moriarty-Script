# Threat model

Moriarty combines two different goals: operating-system hardening and network
privacy. They overlap, but they are not the same, and neither one is a guarantee
of anonymity. This document states what each component protects against, from
which actor, and under which conditions.

## Goals

- **Reduce host attack surface**: fewer kernel information leaks, fewer rare
  protocol handlers reachable, fewer unprivileged primitives available to an
  attacker who already runs code.
- **Reduce network metadata exposure**: keep DNS queries off the local network
  and away from the ISP resolver, and avoid advertising the hardware identity
  across sessions.
- **Stay recoverable**: back up every managed file and provide a restore path.

## Non-goals

- Anonymity or resistance to a global adversary.
- Protection against a compromised root account, malicious firmware, physical
  access, or a compromised upstream resolver.
- Firewalling, intrusion detection, or application sandboxing.
- Patching kernel or application vulnerabilities.

## Actors and assumptions

| Actor | In scope | What they can observe or do | Effect of Moriarty |
|-------|----------|-----------------------------|--------------------|
| Passive observer on the local link (Wi-Fi, LAN) | Partially | MAC addresses, mDNS/LLMNR traffic, plaintext DNS, destination IPs, SNI | DNS content hidden; mDNS announcements suppressed; MAC stable per boot, not per network join |
| ISP or recursive resolver | Partially | DNS names and timings when queries are not encrypted | Queries routed through dnscrypt/DoH, assuming no bypass |
| Access point or network operator | Partially | Association logs, DHCP leases, traffic volume and timing, SNI | Per-boot MAC and DHCP identifiers; traffic metadata still visible |
| Opportunistic remote attacker | Partially | Exploits against exposed services and kernel primitives | Hardening raises the bar; it is not a security boundary |
| Local unprivileged user | Partially | Kernel information, some attack primitives | `kptr_restrict`, `dmesg_restrict`, BPF/io_uring restrictions |
| Root, physical access, malicious firmware | No | Everything | Out of scope |

Assumptions: Arch Linux with systemd and NetworkManager, a single-user
workstation, system-wide DNS through `resolv.conf`, and no VPN or Tor in front.

## Component matrix

| Component | Protects against | Does not protect against | Conditions and limits |
|-----------|------------------|--------------------------|-----------------------|
| Encrypted DNS (`dnscrypt-proxy` on `127.0.0.1:53`) | Local observers and the ISP resolver reading DNS questions; DNS-based censorship or logging by the local resolver | Destination IPs, HTTPS SNI, traffic analysis, a malicious or compelled upstream resolver | `/etc/resolv.conf` must point to `127.0.0.1`; NetworkManager DNS must stay disabled; systemd-resolved must not keep foreign upstreams; applications with their own resolver (some browsers' DoH, VPN clients, static binaries) bypass it |
| Resolver pinning (`dns=none`, `resolved` drop-in, empty `FallbackDNS`) | Silent fallback to DHCP-provided DNS when the proxy fails | Applications that ignore the system resolver | A failed proxy leaves the host without DNS by design; `--check` reports it |
| Bootstrap query | Nothing by itself | Reveals that a dnscrypt/DoH client is starting and which resolver list it fetches | Plain DNS to Quad9 is used once to fetch the resolver list; unavoidable before encrypted transport exists |
| MAC randomization (`stable` cloned MAC) | Long-term tracking by the hardware MAC across networks; OUI-based device fingerprinting | Association logs, captive portals, 802.1X identity, DHCP fingerprinting, traffic correlation; correlation within the same boot | Applied by NetworkManager on managed devices; some drivers ignore it; a reboot is required for the new identity; the MAC stays stable during a boot so DHCP does not flap |
| DHCP identity (`client-id=stable`, no hostname, DUID `ll`) | Hostname disclosure and cross-network correlation through DHCP identifiers | DHCP server logs, lease history, option-order OS fingerprinting, the MAC itself | Server-side records still exist; static configurations are not covered |
| IPv6 privacy (`stable-privacy` IID, `ip6-privacy=2`) | Address-based tracking through a stable interface identifier | Prefix-level tracking, router/neighbour logs, applications that pin addresses | Only affects addresses generated by the host; IPv6 must be present on the link |
| sysctl hardening | Kernel pointer and dmesg leaks, weak ASLR, unprivileged BPF/io_uring/userfaultfd, ICMP redirects, source routing, martian logging gaps, core dumps, SysRq | Application bugs, kernel CVEs, malicious root, hardware or firmware issues | Some keys depend on kernel configuration and are reported as `unsupported`; `kexec_load_disabled` and module policy are irreversible until reboot; `io_uring` and unprivileged BPF restrictions can break legitimate workloads |
| Module blacklist (`install ... /bin/false`) | On-demand loading of uncommon protocol and filesystem handlers by unprivileged or accidental paths | Modules already loaded, built-in drivers, privileged `insmod`, vulnerabilities in in-use modules | Not a CVE fix; can break ISO/squashfs mounts, exotic filesystems, and some VPN or container setups |
| Avahi publishing disabled | mDNS announcements of hostname, addresses, and services to the local link | Active scanning, ARP/DHCP visibility, other announcing services (SSH, Samba), multicast queries the host still sends | Avahi must accept `disable-publishing` in `[publish]`; the service must be running in query-only mode |
| UFW sysctl alignment | UFW overriding Moriarty's `rp_filter`/`log_martians` values | Any actual firewalling | UFW is neither installed nor enabled by Moriarty; only its sysctl file is aligned |
| Backups and restore | Loss of the previous configuration after a failed or unwanted apply | Confidentiality of the backup contents, off-system disaster recovery | Backups live under `/root` with `0700`/`0600`; the manifest is SHA-256 checked; anyone with root can read them |

## Privacy is not security

A few common misconceptions, stated explicitly:

- Changing the MAC address does not make a device anonymous. The access point
  still logs the association, the DHCP server still sees the lease, and traffic
  patterns still identify the host. It only removes the long-lived hardware
  identifier from casual observation.
- Blocking modules does not make the kernel immune to vulnerabilities in those
  modules. It removes code paths that are not needed, but built-in drivers and
  already-loaded modules remain, and a privileged attacker can load others.
- Encrypted DNS hides the question, not the answer's destination. The server
  still sees the client IP, and the network still sees which IP and SNI are
  contacted.
- Kernel hardening raises the cost of exploitation. It does not contain a
  compromised process, and it does not replace patching, sandboxing, or a
  firewall.

## Verifying the claims

`moriarty.sh --check` and the report written by a normal run verify the
functional state (sysctl values, resolver path, NetworkManager defaults, module
rules). They do not prove the absence of leaks. The integration protocol in
[TESTING.md](TESTING.md) describes how to record evidence on real hardware, and
which scenarios are still unverified.
